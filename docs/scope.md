# gastar-app — Product

## Goal

Personal finance PWA for Argentina. Answers two questions:

- How much money do I have?
- How is my month going?

## Language policy

- UI text: Spanish.
- Everything else (code, routes, DB schema, identifiers, docs): English.

## Stack

| Concern | Choice |
|---|---|
| Framework | SvelteKit |
| ORM | Drizzle ORM |
| Database | Postgres |
| Hosting | User's VPS, via Dokploy |
| PWA | `@vite-pwa/sveltekit` |
| Auth | Better Auth |

## Auth

- Email + password, or "Continuar con Google" above the form on Ingresar / Crear cuenta (on only when the server has `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`). Public sign-up; email verification is required before sign-in with a password. A Google profile whose email Google has not verified is refused (no user, no session, no email). A Google user with an existing account of the same email joins it only when both emails are verified; an unverified password account is refused and Ingresar shows "Ya hay una cuenta con ese email sin verificar. Entrá con tu contraseña y verificá el email." Cancelling at Google shows "Cancelaste el ingreso con Google.", any other failure "No pudimos entrar con Google. Probá de nuevo." Only name and email are used; the Google picture is not stored.
- Single user at launch; family/friends may be added later (small scale).
- Phone OTP: future, not MVP.
- Password reset: by emailed link (sent through Resend). Links last 24 hours (verification) and 1 hour (reset).
- Screens: Ingresar / Crear cuenta are the entry (tabs, no back link); every other signed-out screen has "Volver" at the top. A wrong password keeps the typed email, clears the password and focuses it. After sign-up, "Revisá tu email" names the address and offers a rate-limited "Reenviar" (60 s countdown). The password-reset confirmation is neutral and never says whether the address has an account. An expired verification link (`/verify-email`) shows the address pre-filled when this browser remembers the one it was sent to (local storage, per browser), so asking for a new link is one tap; an expired reset link offers "Pedir otro" first.
- Every user's data is isolated from every other user's.
- Shared accounts between users: **future**. The data model must leave this door open (see data-model.md).

## Locale & formatting

- Currency display: `$1.234.568` (ARS), `US$1.234,56` (USD); no space after the symbol, ARS never shows decimals.
- Amount colors: green = positive, red = negative, blue = transfer, never a minus sign. Group totals are neutral (red when negative); savings and informational figures (per day, limits) are neutral.
- Amount input: comma as decimal separator (USD only).
- Manual ARS amounts, initial balances and exchange rates are whole pesos; USD amounts have up to 2 decimals. Amounts imported from Mercado Pago or a Banco Galicia statement keep their cents, and editing may keep a movement's existing non-whole amount; non-whole ARS values display rounded half-up.
- Dates: `dd/mm/aaaa` (e.g. `29/02/2024`); date inputs are a custom calendar (week starts Monday, Spanish), never the native date input.
- Timezone for "month" boundaries and default dates: `America/Argentina/Buenos_Aires`.

## Layout

- Top bar (sticky, every app screen): optional back link, today's date as an eyebrow above the screen title, a bell linking to Avisos (with the alert count as a badge) and an avatar (initials) linking to Profile. Bottom-nav tabs have no back; every other screen has an "up" back to its parent (new-movement returns to the screen it was opened from). Going up pops history like a native stack: back ‹, close ✕, Cancelar and a save that returns to the parent go back to it when it is the screen the user came from (so the edge swipe-back matches), otherwise they replace the current entry with the parent; after a reload the history is unknown and they always replace. Tabs, month arrows, the currency switch and list filters replace the current entry instead of adding one. In the installed PWA (standalone mode) a swipe from the left edge on any screen with a back or close control does the same as that control (not on tabs, auth screens or over a drawer); in a browser tab the system gesture applies. Without JavaScript they are plain links to the parent. Screens have no action buttons under the bar; Accounts and Categories end their list with a "+ Nueva …" row. No currency control: each screen states its own currency, and amounts are never converted or summed across currencies, except inside the Plan, which converts USD into pesos at the plan rate.
- Bottom nav: Inicio | Movimientos | Create movement (center "+") | Plan | Reportes.
- Profile page (back to Inicio): the user's initial, name and email, then four groups:
  - What the user manages: "Cuentas" and "Categorías" (with the number of active ones) and "Vinculaciones" (leads to `/profile/vinculaciones`, which lists the connections: Mercado Pago, only when its OAuth app is configured, with value "Vincular", "Vinculado" or "Reconectar", leading to `/profile/mercado-pago`; and Banco Galicia, always, with value "Configurar" or "Configurado", leading to `/profile/galicia`; the inbox is reached only from the Home imports pill, shown while Mercado Pago is linked or a Galicia pesos account is chosen).
  - Identity: "Nombre", edited in place (Enter or blur saves, with a Deshacer toast; an empty or too long name is not saved and keeps the old one), and "Contraseña", a "Cambiar contraseña" drawer over Profile (current + new password, min 8; revokes all other sessions, this one stays signed in). `/profile/password` is the same form as a page. A user who signed up with Google has no password: the row reads "Crear contraseña" and asks only for the new one, allowed when the session is at most 5 minutes old; an older session shows "Confirmar con Google" (a fresh Google sign-in that returns to the same screen) instead of the form.
  - "Tema" (light / dark / system) as its own card.
  - "Cerrar sesión", and a quiet red "Darme de baja" link at the end: the "¿Darte de baja?" drawer lists what is erased with real counts (accounts and movements, categories, plan and fixed payments; only what applies), asks for the password (a user without one confirms with Google instead and sees which account is being deleted) and warns it cannot be undone; see Deletion. `/profile/delete` is the same as a page. Financial accounts keep "Eliminar cuenta".

## Design

- Tone: classic, serious-bank feel.
- Inspiration: [arqfinance.com/en-AR](https://www.arqfinance.com/en-AR) — particularly font and buttons.
- Observed from ARQ:
  - Fonts: Beausite Classic (text), Beausite Fit (display) — commercial (Fatype), cannot ship without a license.
  - Pill (fully rounded) buttons, light font weights.
  - Palette: deep green `#00301c`, off-white `#f4ece6`, taupe `#776d65`, lime accent `#f0ff9c`, burgundy `#3e0f00`, blue `#5db3e8`.
- Light and dark themes required.
- Theme: shadcn/ui preset (bJMUTPE2), adapted: warm cream neutrals (no pure white in light), emerald primary, stone near-black dark mode, hairline borders, small radii.
- Typeface: **Geist Mono** (@fontsource-variable/geist-mono) for everything, amounts included.
- List interaction pattern: tapping a list item opens a detail page with Edit and Delete actions — no inline row actions. Create and edit share the same form.

## Screens (MVP)

### Dashboard

- Currency tabs `ARS | USD` (two toggle pills, "Pesos" / "Dólares"), stored in the `currency` cookie; default ARS. Currencies are never converted or summed together.
- For the selected currency:
  - Total balance: all accounts of that currency, **including archived**.
  - Month balance: incomes − outcomes (transfers excluded).
  - The dashboard always shows the current month; there is no month navigation.
  - Top 3 categories by net outcome, each with amount and %.
- Below the balance card, a "Disponible para gastar" card (hidden when there are no accounts in the selected currency) showing the one plan, which covers both currencies, with the same figures as the `/plan` summary (always in pesos):
  - With a plan for the current month: "Disponible para gastar · {mes}", the amount, the status as text ("Vas bien", "Atención", "Te pasaste"), "{monto} por día · quedan N días" and a "Ver plan" link to `/plan`.
  - No plan: "Todavía no tenés un plan.", "Con tus ingresos, pagos fijos y ahorro calculamos cuánto podés gastar por día." and a "Crear plan" link to `/plan/setup`.
  - A one-month plan of a past month is treated as no plan and adds "Tu plan de {mes} terminó.".
  - With a plan and something left to spend, the card also draws the month's variable spending (outside fixed payments, plan pesos) day by day against an even pace of the month's budget, with a pill reading "{monto} por debajo del ritmo", "{monto} por encima del ritmo" or "En el ritmo". No chart without a plan or a budget.
- "Próximos vencimientos" (per selected currency, never converted; hidden when there are no active fixed outcomes in it): "Pagaste {pagado} de {total}" with a meter, "Pagaste todos los pagos fijos de {mes}." when all are paid, and a horizontal row of cards for the unpaid fixed payments still due this month (today or later, with "hoy", "mañana" or "en N días"), each linking to the rule. Past-due unpaid payments get no card; there are no overdue states.
- Last 10 movements in the selected currency, with a "Ver todos" link to `/movements?currency=`.

### Reportes

- Route `/reports`, a bottom-nav tab (no back link), h1 "Reportes".
- Currency tabs `ARS | USD` as on the dashboard; one currency per screen, never converted or summed. No accounts in the currency (archived counted): "No tenés cuentas en {pesos|dólares}." + "Crear cuenta" (no month navigation). Accounts but no movements in the currency in the last 6 months: only "Sin movimientos en {pesos|dólares}.".
- Month: `?month=YYYY-MM` with previous / next navigation; a future or invalid month falls back to the current one; "Mes siguiente" is disabled on the current month.
- For the selected currency and month (archived accounts included, transfers excluded):
  - Totals: Ingresos, Gastos and Resultado (income − outcome, shown without a sign and coloured by polarity: green positive, red negative, neutral zero; equals the dashboard month balance for the current month). Ingresos and Gastos sit side by side.
  - Income and outcome bars for the 6 months ending at the selected month, with a legend; the selected month is highlighted. Each pair links to its month: months change with ‹ › or a tap on a bar (no swipe).
  - Gastos por categoría: top 4 categories by net outcome plus "Otros" (last, not a link), as horizontal bars: name, %, amount and a bar (no donut). With no categorised spending: "No hay gastos con categoría en {mes}." and "Por día" is hidden.
  - Por día: outcome ÷ elapsed days (the whole month for past months).
  - Gasto más grande, linking to the movement; hidden when there are no outcomes. Por día and Gasto más grande share a row.

### Plan

- Route `/plan`, a bottom-nav tab (no back link), h1 "Plan". One plan per user, always in ARS (no currency tabs): USD items convert to pesos at the plan rate, and this is the only place the app converts. No accounts at all: "No tenés cuentas." + a link to create one.
- Recurring incomes and payments ("Ingresos fijos", "Pagos fijos"): monthly rules with description, amount (in the account's currency; ARS in whole pesos), due day 1–31 (clamped to the month's last day), account and category.
- Each row shows description, amount, "Día N", account and a status as text: "Cobrado" / "Pagado" when a movement linked to the rule exists in the current month, else a neutral "Pendiente · día N" (no overdue or upcoming states, nothing red). A rule is paid when a movement linked to it exists in the current month.
- There is no "Registrar": a payment is registered as a normal movement and links itself to its rule. A new income or outcome (manual form, import approval, quick approve, automatic approval after a sync or statement upload) with no link yet is linked, in the same transaction as its insert, to an active rule of the user when the type is the same, the account's currency equals the rule account's currency, the rule has no linked movement yet in the movement's Buenos Aires month, and the descriptions are equal after trimming, lowercasing and stripping accents. With several matches the rule whose day of month is closest to the movement's day wins. A rule has at most one linked movement per month. The rule's amount follows reality: when a linked **payment** (outcome) differs from the rule's amount, the rule takes the movement's amount (ARS rounded half-up to whole pesos), only if the movement's month is not earlier than the month of the rule's latest linked movement; the rule detail then shows "Antes $X" under the amount, until the amount is edited by hand. Deleting or undoing that charge (or unlinking it) puts the previous amount back when no later linked movement exists. Income rules never change their amount or "Antes" from a link (a salary can arrive in parts). Unpaid rules still count as pending in the plan math; the plan figures are unchanged.
- Explicit link: in the import review (drawer and `/imports/[id]`) an optional picker "Es el pago fijo" ("Es el ingreso fijo" for a credit) lists the active rules of the item's currency and type; choosing one links the movement to it (explicit wins over description matching; if that rule already has a movement that month, nothing is linked). A movement's detail has a "Pago fijo" ("Ingreso fijo") row with the same constraints to link or unlink an existing movement ("Ese pago fijo no está disponible o ya tiene un movimiento ese mes." when it cannot). Transfers never link.
- A rule is inactive if the rule, its account or its category is archived; inactive rules are listed under "Inactivos" with the reason ("Archivado", "Cuenta archivada", "Categoría archivada") and does not count in the plan. A fixed payment born from a purchase in cuotas ends by itself after its last month ("Terminado", under "Inactivos", never archived) and its detail shows "Última cuota" with that month; it only links to the purchase's own payments (never by description) and keeps its amount. When the first cuota's statement line arrives, the last month moves to that statement's closing month plus the remaining cuotas if that is later; for a purchase made after a closing, the month right after the purchase has no cuota, so the fixed payment may show as pending that month. Undoing the approval of the first cuota is refused while a later cuota is linked to its fixed payment.
- A rule's detail `/plan/recurring/[id]` is also its editor (no `/edit` route; the old URL is a 404): amount, description, Cuenta, Categoría and Día del mes (1–31 picker) save on their own with a Deshacer toast; actions are "Desactivar" / "Activar" and "Eliminar" (confirmation, not undoable; the movements already registered are kept). When it does not count in the plan the reason is shown and Categoría stays editable. New rules open as a drawer over `/plan` (Cancelar / Guardar; Guardar waits for amount and description). Another user's or a missing rule is "Movimiento fijo no encontrado." (404).
- Empty state: "No tenés pagos ni ingresos fijos." with "Agregar pago fijo" and "Agregar ingreso fijo".
- Plan summary (top of `/plan`): "Disponible · {mes}" with the hero amount in pesos, a status as text ("Vas bien", "Atención", "Te pasaste"), "{monto} por día · quedan N días", and the figures Ingresos, Pagos fijos, Ahorro, Para gastar, Gastado and Disponible (Disponible = Ingresos (active income rules) − Pagos fijos − Ahorro − Gastado). Gastado counts the month's outcomes on accounts of both currencies (archived accounts included, transfers excluded) except those linked to an active rule, whose full amount is already in Pagos fijos; each USD subscription is therefore counted once, when it is charged in USD. USD rules and spending convert at the plan rate; each figure is summed per currency and converted once (half up to whole pesos).
- Plan rate ("Cotización"): below the figures a link row opens the rate drawer (`/plan/rate`, "Cotización del plan", "1 USD ="). By default the rate is the most recent ARS↔USD transfer's (not in the future): "Cotización: $1.585 (última compra, 10/11)". A manual rate overrides it ("Cotización: $1.600 (manual)"; whole pesos, "Usar la última compra" removes it). USD fixed-payment rows show "US$ X ≈ $Y". With no transfer and no manual rate the row reads "Sin cotización", USD rows say "Sin cotización", USD items stay out of the pesos totals and the note "Sin cotización: lo que está en dólares no se suma a los totales." shows; the plan is never blocked.
- Limits: "Límites por categoría" lists each limit as "{gastado} de {límite}" with a progress meter and, as text, "Vas rápido" or "Te pasaste". Each limit opens a drawer over `/plan` (`/plan/limits/[categoryId]`: tap the amount to edit, autosave with Deshacer, "Usar promedio", "Eliminar límite" with confirmation) and "Agregar" opens the new-limit drawer (`/plan/limits/new`; its category list hides categories that already have a limit, and a "Moneda" control picks Pesos or Dólares). A limit keeps its own currency (one limit per category); spending in the other currency converts into the limit's currency at the plan rate. Savings are in ARS (a % of the total ARS income, USD income converted, or a fixed amount in whole pesos). The Ahorro figure opens a drawer (`/plan/savings`): list rows with a checkmark, a pick saves on its own with Deshacer, "Otro" takes a % or amount. Deshacer never closes these drawers. "Eliminar plan" (with confirmation) on `/plan` deletes the plan and its limits but keeps the rules.
- No plan for the current month: "Sin plan" with "Crear plan" (and "Tu plan de {mes} terminó." after a one-month plan ends).
- First-setup wizard `/plan/setup?step=N` ("Crear plan"), 5 steps with a 5-segment progress bar: Ingresos (the /plan income rows, "Inactivos" greyed, "+ Agregar" opens the new-rule drawer without leaving the step), Pagos fijos (same for payments), Ahorro (Nada, 10 %, 20 % or Otro, as `/plan/savings`; "Siguiente" creates the plan), Límites ("+ Agregar" opens the new-limit drawer; "Usar sugeridos" sets the average of the last 3 months for every expense category without a limit) and Resumen (the wizard works over both currencies at once; "Usar sugeridos" suggests pesos averages, or dollars when a category has no pesos spending; Ingresos, Pagos fijos, Ahorro, Para gastar, the switch "Usar este plan todos los meses" and "Guardar plan"). Adding happens in drawers over the step; there are no inline forms. The bar has Cancelar (step 1) or Atrás on the left (1/3) and Siguiente or Guardar plan on the right (2/3). Without a step and with a current plan it redirects to `/plan`; steps 4-5 without a plan go back to step 3. Checked stores the plan for every month; unchecked only for the current month. Saving returns to `/plan` with "Plan guardado.". ARS amounts are whole pesos.

## Rules

- ARS and USD are separate ledgers for balances, Reportes and movements. The only link between them is a transfer between accounts of different currencies. The plan is the only place that converts (at the plan rate; balances are never converted).
- Exchange rate is always expressed as "1 USD = X ARS", entered manually per transfer, in whole pesos. No automatic rates.
  - USD → ARS: `destination = amount × rate`.
  - ARS → USD: `destination = amount ÷ rate`.
  - Rounding: half-up to whole pesos into ARS, half-up to cents into USD.
  - Example: 100 USD at rate 1500 → 150.000 ARS. 150.000 ARS at rate 1500 → 100 USD.
  - Same-currency transfer: no rate; destination amount = amount.
- Transfers never count toward month balance and have no category.
- Balances are always computed, never stored:
  `balance = initial_balance + incomes − outcomes − transfers_out(amount) + transfers_in(destination_amount)`.
- Categories have no type — both incomes and outcomes can use any category.
  - Category net (per currency, per period) = outcomes − incomes. Example: a 100 dinner outcome + a 50 reimbursement income in the same category = net spend 50.
  - Top 3 = categories with the highest positive net outcome.
  - % = category net ÷ sum of all positive category nets.
  - Categories with net ≤ 0 are excluded from the top 3.
- Categories are shared across currencies; their stats are split by currency.
- Accounts have no types. Each has: name, currency, initial balance, icon, color.
  - Currency cannot change once the account has movements.
- Deletion:
  - An account or category referenced by any movement cannot be deleted — the UI offers Archive instead.
  - An unreferenced account/category is hard-deleted, with confirmation.
  - Archived items: cannot be selected for new movements; movements that already reference them keep showing them and can be edited without losing the reference; can be unarchived.
  - Archived accounts still count toward total balance.
  - Movements: hard delete, with confirmation.
  - User account: hard delete, immediate and irreversible, of the user and all their data (movements, recurring rules, plans and limits, categories, accounts, sessions) in one transaction; then sign-out to the login page. A user without a password confirms by signing in with Google again: deleting needs a session at most 5 minutes old, otherwise "Confirmar con Google" returns to the same screen; picking another Google account lands on that account page and never deletes the first.

## Mercado Pago import

- Optional, per user: on only when the server has `MP_CLIENT_ID`, `MP_CLIENT_SECRET` and `MP_TOKEN_KEY` (off: the Profile "Vinculaciones" row is hidden and the Mercado Pago routes answer 404). Each signed-in user links their own Mercado Pago account through OAuth (PKCE) and gets the full import for themselves; nobody sees another user's import.
- Profile → "Vinculaciones" → "Mercado Pago" leads to `/profile/mercado-pago` (back to Vinculaciones), which has three states: not linked, one card saying what gets imported and a single "Vincular Mercado Pago"; linked, settings only (no link to the inbox, which is reached from the Home pill): "Entra en" (a list row that opens the active ARS accounts and saves on pick, with Deshacer; the first pick has no Deshacer), "Desvincular" (the "Importar desde" date lives on Vinculaciones, which this screen links to); and "Reconectar" when Mercado Pago no longer accepts the saved access (revoked, or the token could not be renewed). The Vinculaciones row shows "Vinculado" when linked, else "Vincular" or "Reconectar". The inbox `/imports`, titled "Importados" (back to Inicio), is source-agnostic: an item's account is the item's own and its counter accounts exclude it. The sync line ("Sincronizar") shows only while Mercado Pago is linked. With no usable connection, no pending items and none auto-approved in the last 30 days `/imports` redirects to `/profile/vinculaciones`; with pending items it lists them (no sync line). While a reconnect is pending it still lists the items, hides "Sincronizar" and offers "Reconectar". The inbox has no settings links.
- Disconnecting deletes only the stored connection: imported items, rules and sync state stay. The user can also revoke access from their Mercado Pago account. Changing the receiving account starts the sync over for the new account; items are never duplicated.
- "Importar desde" (on `/profile/vinculaciones`, shown when Mercado Pago or Gmail is available; one date per user for Mercado Pago and Gmail alerts, never for Banco Galicia statements; `/profile/mercado-pago` only points to it): the minimum date of every automatic import, picked on the calendar and saved on its own with Deshacer; at most 12 months back and not in the future. Moving it earlier pulls Mercado Pago payments and the release report, and Gmail card alerts, from that day to now; moving it later drops the pending Mercado Pago and Gmail-alert items before it. It is disabled while a sync runs. It can be used at any time, leaves the regular sync window (`synced_until`) untouched, and never duplicates or changes items already imported, approved or rejected.
- Tokens are stored encrypted, renewed automatically before they expire, and never shown to the client.
- Sources, pulled on "Sincronizar ahora" (both) and automatically (payments every `MP_SYNC_INTERVAL_HOURS`, default 1; the release report once a day at 08:00 Buenos Aires, or on the first run after a start if that day's was missed, and skipped when a manual sync already brought it within the hour before):
  - Payments (`/v1/payments/search`, both directions, from the latest imported payment minus three days; incoming amounts are net of MP fees): shown at once. Only approved payments become items; credit-card payments never touch the balance and are skipped. A refund or chargeback becomes a separate "Devolución" item in the opposite direction when the payment is still approved (partial refund) or was already imported and not rejected.
  - The Mercado Pago "Liquidaciones" (release) report (`/v1/account/release_report`), requested in the background (it waits minutes in MP's queue): only `payout` rows (withdrawals and transfers out), and `asset_management` rows (daily yields, signed: a debit is a loss); payments come from the payments search. A payout with an external reference is titled "Pago en comercio" (pre-filled Gasto); without one, "Transferencia o retiro" (pre-filled Transf.). Mercado Pago emails the account owner "Tu reporte de liquidaciones está listo" for every report, whatever the config's `notification_email_list` holds and with no API or panel setting to turn it off for a personal account; that is why the automatic sync requests it only once a day. A linked account with no release config gets one created (only the columns the import reads, Buenos Aires time, empty email list); an existing config is never replaced: Gastar edits it with a PUT of only the documented writable fields (never `scheduled` or other read-only keys) that empties its email list (no extra recipients), appends any import column it lacks to the user's own, and sets English headers if they were translated. Gastar never creates settlement reports and leaves any settlement config in the user's account untouched. The report cursor (`synced_until`) is shared with the settlement report this one replaced, so a sync continues from where that one stopped, and item keys (`yield:<day>`, `payout:<id>:out`) are unchanged, so earlier imports are not duplicated.
- Items keep the real time of day (Buenos Aires).
- Each payment, yield or payout becomes a pending item in a separate inbox, grouped by day, with the pending count shown in the Home pill. Nothing touches balances or movements until an item is approved (by the user, or automatically: see below). The inbox (`/imports`, opened from the Home pill) starts with one line: the last sync ("Hace 2 h") and "Sincronizar"; while a run is in progress that line becomes "Sincronizando…" / "Puede tardar unos minutos." (no count, no "Sincronizar") and a run seen on the page ends with "Listo. N movimientos nuevos." (", M aprobados automáticamente" when the run auto-approved any). "Aprobar N sugeridos" is a full-width button of its own (with a confirm). Tapping a row opens its review as a drawer over the inbox (shallow route); `/imports/[id]` is the same review as a page for direct URLs (404 unless it is the user's and still pending). A suggested row ("{category o cuenta} · sugerido") has a quick "Aprobar"; an unknown one ("No sabemos qué es") a "Revisar" shortcut.
- Deshacer of a quick "Aprobar" (`/imports?/undoApprove`) runs in one transaction: it deletes the movement the approval created and returns the item to pending. It refuses (nothing changes, "No se pudo deshacer." toast) when the movement was edited or deleted meanwhile, or the item is no longer an approved one. It never touches rules: a quick approval remembers nothing.
- Automatic approval (always on, no setting): after every sync run (scheduled, "Sincronizar", "Importar desde"), every pending item a usable rule recognizes (exactly the "sugerido" ones) is approved with the rule's values, as a quick "Aprobar" would, without creating or changing any rule. Items no rule recognizes, refunds, and items whose movement would not validate (archived category or account, etc.) stay pending for review. The inbox shows a line "N aprobados automáticamente" (items auto-approved in the last 30 days whose movement still exists; hidden when 0) that opens `/imports/auto` (back to Importados): newest first, each row with title, amount, category or account and date, and "Deshacer", with the same semantics and refusal as the quick approve's. An item undone there is never auto-approved again: it stays for manual review ("Aprobar N sugeridos" and the quick "Aprobar" still offer it). "Aprobar N sugeridos" and the quick "Aprobar" stay for items that become suggested between syncs.
- Yields are one item per day, with the exact net amount: gains minus losses of that Buenos Aires day. A positive day is a credit; a negative day is a debit (pre-filled Gasto, and it does not share the remembered rule of positive yields); a day that nets zero has no item.
- Review: a one-line summary (amount, date and time, the original description below, ellipsized) is read-only and, for an item no rule suggests, "No sabemos qué es: elegí el tipo."; the user edits type (a credit offers Ingreso / Transf., a debit Gasto / Transf.), description, category (income/outcome) or counter account (transfer: an active account of the item's currency, not the item's own). A debit transfer goes from Mercado Pago to the counter account; a credit transfer comes from it. The description is required (prefilled from the original; "Aprobar" is disabled while empty). "Aprobar" creates the movement and returns to the inbox (no auto-advance); "Descartar" asks "¿Descartar movimiento?" and rejects the item for good (the sync never re-imports it). Both confirm with a toast.
- Learning: approving remembers the choice (type, category or counter account, description as alias) under the strongest key of the item: counterparty (transfers), then merchant, then kind (yields, each payout label, account funds); refunds teach nothing. The next matching pending item is pre-filled and shows "… · sugerido" in the list. Only the first matching rule is used, and only while its category or account is still active; otherwise the item gets defaults (payments by direction; yields income (a negative-yield day outcome); "Pago en comercio" outcome; other payouts and account funds transfer; anything else asks to review the type). Categories are never created automatically. When the review has a fixed payment picked ("Es el pago fijo" / "Es el ingreso fijo") and "Recordar para …" is on, that link is stored on the rule too: later matching items, automatic approval included, link to that rule even when the description differs (still at most one linked movement per rule per month; a deleted rule just stops linking).

## Gmail connection

- Optional, per user: on only when the server has `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET` and `GMAIL_TOKEN_KEY` (off: the Vinculaciones row is hidden and the Gmail routes answer 404). It uses its own Google Cloud client, never the sign-in one.
- Profile → "Vinculaciones" → "Gmail" (value "Vincular", "Vinculado" or "Reconectar") leads to `/profile/gmail`. Not linked: a card saying that only the Visa and Banco Galicia Mastercard purchase-alert emails are read, that the purchase data is stored and never the email, a note that Google shows "Google no verificó esta app" (continue with "Configuración avanzada" → "Ir a Gastar (no seguro)"), and "Vincular Gmail" (OAuth with PKCE, read-only `gmail.readonly`, offline access, consent every time so a refresh token always comes back). Linked: the Gmail address, "Vinculado" and "Desvincular" (revokes the access at Google; items already imported stay). When Google no longer accepts the saved access, "Reconectar".
- If the user does not grant mail access, the link is rejected, the grant is revoked and nothing is stored ("Para vincular Gmail tenés que permitir que Gastar lea tus mails.").
- Visa purchase alerts: the sync reads only mails from the two Visa alert senders whose subject is exactly "Alerta de Compras Visa" and that Gmail itself authenticated as Visa (DKIM and DMARC pass for visa.com in the first `Authentication-Results` header); anything else is skipped without a trace. The first sync, and any move of "Importar desde" earlier, reads from that day (backfill; alerts already stored are not duplicated); moving it later drops the pending alert items before it. It runs every 15 minutes (`GMAIL_SYNC_INTERVAL_MINUTES`) and from "Sincronizar" in Importados (which shows when Mercado Pago or Gmail is linked). Only the parsed fields of each alert are stored (card last 4, merchant, country, currency, amount, foreign flag, transaction type, time received); the mail, its subject, headers and links are never stored or logged. A card-alert mail that does not parse is not guessed: nothing is stored for it and the run ends with the error code `parse` ("algún mail de alertas de tarjeta no se pudo leer").
- Banco Galicia Mastercard purchase alerts: the same sync also reads mails from `alertas@misconsultas.com.ar` whose subject is exactly "Aviso de consumo con tarjeta", that Gmail authenticated for misconsultas.com.ar (DKIM and DMARC pass in the first `Authentication-Results` header) and whose intro names a Mastercard issued by Banco Galicia; anything else is skipped without a trace. A state other than "APROBADA" is skipped too. The amount is read as es-AR (`78.993,00`), "PESOS" is pesos and "DOLARES"/"U$S"/"USD" dollars (any other currency does not parse), the location decides the foreign flag, and the installment count ("Cantidad cuotas") is stored as well. An alert of more than one installment becomes the item of the purchase's first cuota (the total divided by the cuotas; the first carries the remainder), shown as "N cuotas de $X", whose only type is Gasto and which has no "Es el pago fijo" picker. A remembered merchant rule auto-approves it like any other item; otherwise it waits in the inbox. Approving it (by hand or automatically) books that first cuota and creates a fixed payment of "$X" per month for N months (X is the total divided by N, whole pesos in pesos; it never follows the statement's cuota amount), with its last month ending the purchase; undoing the approval removes that fixed payment too. A "COMPRA REVERSADA" alert (a cancelled pre-authorization, which never reaches the statement) cancels the latest earlier purchase alert of the same card, amount and merchant. If neither became an item, neither ever does. If the purchase is still a pending item, that item is removed. If the purchase was already approved, or there is no purchase to cancel, the reversal becomes a pending credit item so the refund can be recorded. For an approved installment purchase the credit is the booked first cuota (not the total) and its fixed payment is deactivated ("Desactivado", can be activated again).
- Cards: an alert of a card the user has not set up waits, and Importados shows one row "Tarjeta Visa ••NNNN: elegí qué es" (or "Tarjeta Mastercard ••NNNN"; above the pending list) that opens `/profile/gmail/cards/visa-NNNN` (`mastercard-NNNN`): "Crédito" or "Débito" (a Mastercard is always credit and shows no choice), "Cuenta en pesos" (required) and "Cuenta en dólares" (optional). For a credit card those two pickers are the Banco Galicia accounts (a saved credit card shows the Galicia ones, and saving writes them there); for a debit card they are the card's own. Saving turns the waiting alerts into items, and so does picking a Banco Galicia account in `/profile/galicia` (alerts stored since linking are converted at that moment, at the next Gmail sync, or when the card is saved). `/profile/gmail` lists the cards ("Visa ••NNNN · Débito", "Mastercard ••NNNN · Crédito") to edit them. A card can only be set up once alerts of it arrived.
- Debit card: each "Compra" alert becomes a pending item of the source "Visa Débito" (kind card purchase, timed) on the card's account of the alert currency (a USD alert goes to the dollar account as it is). Rules, automatic approval and "Es el pago fijo" work as for any item; the merchant name drops a trailing run of masking `x` ("MABERONxxxx" is "MABERON"). An alert whose transaction type is not "Compra" becomes an item that always asks for a review: no rule suggests it and it is never auto-approved.
- Credit card: each alert becomes a pending item with the statement's own source ("Galicia Visa" or "Galicia Mastercard", by the card's network; kind card purchase, a day, no time) on the Banco Galicia pesos or dollar account, key `alert:<message id>`, and the statement confirms it later (see "Banco Galicia statements": alerts and statement lines of one purchase are one item). As for debit, a transaction type other than "Compra" always asks for a review and is never auto-approved.

## Banco Galicia statements

- Always available (no setting or env flag). Profile → "Vinculaciones" → "Banco Galicia" leads to `/profile/galicia` (back to Vinculaciones): "Pesos" (required) and "Dólares" (optional) pick active accounts of that currency and save on pick (with Deshacer; the first pick has none), then "Subir resumen" uploads the PDF of a Visa or Mastercard statement. There are no card accounts: every line lands on the chosen bank account of its currency. The Vinculaciones row shows "Configurado" once the pesos account is chosen.
- The PDF (PDF only, up to 5 MB and 20 pages) is parsed in memory and never stored or logged. It must be a Galicia statement ("CUIT Banco: 30-50000173-5") and reconcile to the cent in each currency: SALDO ANTERIOR + payments + credits + consumos + charges = TOTAL A PAGAR; otherwise it is rejected with nothing written ("El resumen no cuadra con el total; no se importó nada."). A statement with dollar lines and no dollar account is rejected asking to choose one. Uploads are rate-limited per user.
- Each consumo line becomes one pending item in the same inbox (a debit; a negative line a credit). Installment lines (CUOTA `05/12`) are one item per statement, dated at the statement closing date and titled with the cuota (`BAZAR AVENIDA_CS 05/12`); single purchases are dated at the purchase date. Dollar lines go to the dollar account. All taxes, perceptions and other charges (IMPUESTO DE SELLOS, IIBB, IVA RG 4240, and the like) net with the statement's credits into one item per currency, "Impuestos y percepciones", dated at closing (a debit if positive, a credit if negative, none if zero). The RG 5617 30% dollar perception (DB.RG 5617) and its refunds (DEV.IMP. RG 5617) are skipped: the card is always paid in dollars, so it never applies; they still count toward the statement's reconciliation. Payments ("SU PAGO …") are skipped: the consumos already debit the bank account. "Cuotas a vencer" is ignored.
- Uploading a statement again, or a later one that repeats lines, never duplicates items (keys: network + comprobante + cuota + date + amount; taxes: network + a hash of the statement number + currency). After the upload, automatic approval runs as after a sync, and the inbox opens with "N movimientos nuevos" (", M aprobados automáticamente").
- Rules and defaults are the Mercado Pago ones: a line matches by merchant (the statement reference cleaned of per-transaction codes, lowercased: Visa markers, USD amounts, cuota tokens, a "MERPAGO*" prefix and trailing code tokens go, while "*" and other punctuation inside the name stay; rules learned earlier on the raw reference, trimmed and lowercased, still match as a fallback; Mercado Pago keys are unchanged) and the taxes item by kind. A line's title, default description and "Recordar para …" use that cleaned name in its original casing (`WEBVANS`, `AMERICAN AIR`, installments keep the cuota); the review still shows the original reference; debits default to Gasto, credits to Ingreso; a card credit teaches nothing. A "Diferencia con el resumen" item (below) is titled with that text and the merchant, and a debit one is recognized by the merchant's rule while a credit one waits. Inbox rows name their source ("Galicia Visa", "Mercado Pago") only while the pending items come from more than one source; "Sincronizar" stays Mercado Pago only. The review shows the day only (no time) for statement lines, and the counter accounts of a transfer are the active accounts of the item's own currency. The review has the same "Es el pago fijo" picker and remembered link; an automatically approved line links to a fixed payment by the remembered link or by description (the cleaned merchant name is the movement's title, so "MOVISTAR DA 000000583683789" is "movistar da" next month too).
- Matching with Gmail credit-card alerts (after the reconciliation, per consumo line before inserting): a debit line (not a credit) of a single purchase, or the first cuota (`01/N`) of an installment purchase, matches an alert item of the same network and currency that has no match yet and is dated from 3 days before to 1 day after the line (Buenos Aires day). Tiers, the first with a match wins: (1) installment line: the alert equals the cuota, or the cuota times N within 1%; (2) the exact amount; (3) pesos only: the amounts differ by at most 15% and the cleaned merchant names are compatible (one a prefix of the other); dollars always need the exact amount. Inside a tier: the nearest date, then the most similar merchant name. A matched line creates no item: the alert item stores the line's key as its `alias_key`, so uploading the statement again matches nothing new and duplicates nothing. A pending alert item takes the statement amount (the cuota for an installment); an approved or rejected one is never touched, and a separate item "Diferencia con el resumen · <comercio>" (kind card adjustment, on the same account, dated at the closing) holds the difference, a debit or a credit. Taxes, perceptions and payments still come only from the statement. The later cuotas (`02/N` onwards) of a purchase whose first cuota was approved as an installment item are matched, with the same rule and window, to that item at upload (the line's cuota read as `01/N`); the line's item then takes the purchase's fixed payment, is suggested with its category and description and, being a learned link, is auto-approved as that month's payment (it links only to that payment). The `01/N` line itself matches the alert item as above and creates no item. The reverse order (statement first, alert later) uses the same rule from the alert side: the alert creates no item and its key becomes the statement item's `alias_key` (no difference item). The tolerances and the date window are constants (`galicia/matching.ts`).
- "No apareció en el resumen": a credit alert item still unmatched after two uploaded statements of its network that close after its date is listed in Importados under that heading, each with "Descartar" (undoes its movement with the usual undo rules and rejects the item) and "Dejar" (it stays and leaves the list). Nothing is removed automatically.

## Out of MVP

- Credit-card accounts (statement lines land on the user's bank accounts instead: see "Banco Galicia statements").
- Attachments / receipts.
- CSV import/export (the Mercado Pago import and Banco Galicia statements are the exceptions).
- Shared accounts.
- Phone OTP.
- Push or email notifications (Avisos are in-app only).
- Automatic exchange rates.
- Adjustable (editable) destination amount on cross-currency transfers.
